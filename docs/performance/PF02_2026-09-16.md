# PF02 - Concurrent booking contention result

- Date: 16 September 2026
- Owner: Hai Anh (member 3 - Booking)
- Result: PASS for correctness
- Scenario: 200 authenticated customers submit one booking each for the same room and time.

## Purpose

PF02 verifies that concurrent requests cannot create overlapping reservations. Exactly one request must create a booking, while the remaining requests must receive the expected business conflict response. No request may return 422, 5xx, or time out.

## Functional result

| Outcome | Expected | Actual |
|---|---:|---:|
| HTTP 201 - booking created | 1 | 1 |
| HTTP 409 - room conflict | 199 | 199 |
| HTTP 422 - invalid test data | 0 | 0 |
| Other, 5xx, or timeout | 0 | 0 |

Locust summary:

```text

```

HTTP 409 is an expected successful outcome in PF02 because it proves that the application rejected an already occupied room/time slot.

## Response time observed

| Request | Count | Average | p50 | p95 | Maximum |
|---|---:|---:|---:|---:|---:|
| `POST /auth/login` | 200 | 10,575 ms | 13,000 ms | 14,000 ms | 14,145 ms |
| `POST /bookings (contention)` | 200 | 3,657 ms | 1,700 ms | 9,500 ms | 9,474 ms |

PF02 has no mandatory latency threshold in the specification. The booking p95 reflects deliberate lock contention: 200 transactions compete for one room row, so requests queue while preserving correctness. These values must be reported as measured and must not be replaced with the PF01 search target of 300 ms.

## Conclusion

PF02 passes the concurrency correctness criteria. Under 200 simultaneous contenders, CineNest creates exactly one reservation, rejects the other 199 requests as business conflicts, returns no unexpected errors, and leaves exactly one occupying booking in PostgreSQL.
